# research-pipeline

Automated daily research publishing pipeline. Every day it selects a research
topic from real recent events, performs structured web research, validates the
evidence, writes a Markdown deep-research report, reviews it, commits it to
this repository, and updates an RSS feed.

## Architecture

```text
Scheduler (GitHub Actions, 09:00 Asia/Taipei)
   ↓
Topic Selector   — watchlist scan → event discovery → candidates → scoring (0–35)
   ↓
Research Agent   — questions → web search → evidence objects → research.json
   ↓
Validator        — schema + critical checks (sources, facts↔evidence, bear case…)
   ↓
Writer Agent     — narrative only; report skeleton rendered from research.json
   ↓
Reviewer Agent   — PASS/FAIL gate; FAIL never publishes
   ↓
Git Commit       — research/ + reports/ + memory/ + public/ only
   ↓
RSS Builder      — public/feed.xml + public/index.json
```

- **LLM**: Anthropic Claude (`claude-opus-5` by default) behind an
  `LLMProvider` interface (`src/providers.ts`) — swappable for another vendor.
- **Search**: Anthropic's server-side `web_search` tool behind a
  `SearchProvider` interface — one API key powers both.
- **No servers, no database** — state lives in git (`memory/*.json`).

## Repository layout

```text
reports/YYYY/MM/YYYY-MM-DD-slug.md    published reports (English)
reports/YYYY/MM/YYYY-MM-DD-slug.zh.md Traditional Chinese edition (same data)
assets/YYYY-MM-DD-slug/charts.json    chart data referenced by the site
research/YYYY/MM/YYYY-MM-DD-slug.json structured research data
memory/                               topics / theses / watchlist / companies
prompts/                              agent prompts
schemas/                              JSON Schemas (research, report, memory)
src/                                  pipeline source (TypeScript)
tests/                                unit tests
public/feed.xml, public/index.json    RSS + machine-readable index
.github/workflows/daily-research.yml  scheduled daily run
.github/workflows/maintenance.yml     manual/PR pipeline verification
```

The committed report/research under `2026/08/` is an **example** generated by
mock providers (fictional data, `example.com` sources) to demonstrate the
output format.

## Installation

```bash
npm install
```

## Environment variables

| Variable | Purpose |
|---|---|
| `ANTHROPIC_API_KEY` | required for real runs (LLM + web search) |
| `LLM_MODEL` | optional model override (default `claude-opus-5`) |
| `DRY_RUN=true` | research + write, but no commit/push |
| `FORCE_UPDATE=true` | overwrite an existing same-day report |

Copy `.env.example`, never commit `.env`.
**Without an API key the pipeline runs with mock providers** (deterministic
example data) — useful for tests and structural dry runs only.

## Local execution

```bash
npm run daily                 # full pipeline
npm run daily -- --dry-run    # no commit / push / publish
npm run daily -- --topic "..."          # force a topic
npm run daily -- --date 2026-08-19     # run as a specific date
npm run daily -- --force-update        # overwrite same-day report
npm run research              # stop after research + validation (persists research.json)
npm run validate              # alias of the above validation stop-point
npm run build:rss             # rebuild feed.xml/index.json from reports/
npm test                      # unit tests
npm run typecheck
```

## GitHub setup

1. Create a GitHub repository and push this project.
2. Add the secret (Settings → Secrets and variables → Actions):
   - `ANTHROPIC_API_KEY`
3. Ensure Actions has write permission (Settings → Actions → General →
   Workflow permissions → "Read and write permissions").
4. Trigger a first run manually: Actions → **Daily Research** → Run workflow
   (`workflow_dispatch` supports `topic`, `force_update`, `dry_run` inputs).

## Schedule

`daily-research.yml` runs at `0 1 * * *` UTC = **09:00 Asia/Taipei** daily,
plus manual `workflow_dispatch`. The daily job refuses to run without the API
key secret (it will not publish mock data).

## Pipeline stages

1. Load Memory → 2. Watchlist scan / Discover Candidates → 3. Rank Topics →
4. Select Topic (threshold `minTopicScore=23`; below it: **skip publication**) →
5. Build Research Questions → 6–8. Gather Sources / Extract Evidence / Build
Structured Research → 9. Validate → 10. Write → 11. Review → 12. Persist →
13. Update Memory → 14. Build RSS → 15. Commit/Publish.

Duplicate prevention: candidates matching a topic from the last 30 days are
downgraded to `UPDATE`/`FOLLOW_UP`; the idempotency key is `date + slug`.

## Research schema

See `schemas/research.schema.json`. Highlights:

- every FACT must reference evidence ids; metrics must carry `source_id`
- `>= 3` sources, `>= 2` primary sources
- bear case, kill conditions, and 3–5 validation events are mandatory
- `Structural Bottleneck` requires demand High/Extreme + supply elasticity Low
  + substitutability Hard (enforced by the validator)

## Failure handling

- transient API/search errors: 3 retries with exponential backoff
- LLM schema-validation failures: up to 2 corrective retries, then the
  workflow fails
- validator critical failure or reviewer `FAIL`: pipeline stops, nothing is
  published, the Actions run turns red
- no topic above the score threshold: run ends cleanly with no report

## RSS

- Feeds: `public/feed.xml` (English) and `public/feed.zh.xml` (繁體中文, served
  at `/zh/feed.xml` on the site) — RSS 2.0, latest 50 items, description =
  one-sentence conclusion + executive summary; zh items use the `.zh.md`
  translation with English fallback
- Index: `public/index.json`
- Raw URL once pushed:
  `https://raw.githubusercontent.com/<owner>/research-pipeline/main/public/feed.xml`
- With GitHub Pages enabled (optional): `<siteUrl>/feed.xml`

## How to change models

Set the `LLM_MODEL` env var (e.g. in the workflow) or edit the default in
`src/providers.ts`. To switch vendors entirely, implement `LLMProvider` /
`SearchProvider` (`src/providers.ts`) with another SDK and wire it in
`src/main.ts` — no other module talks to a vendor directly.

## i18n & static site

- The site is bilingual with separated language trees:
  English at `/` + `/reports/<slug>/`, 繁體中文 at `/zh/` + `/zh/reports/<slug>/`,
  with a language switcher on every page. A missing `.zh.md` falls back to the
  English text with a notice.
- The pipeline translates each published report to Traditional Chinese
  (`src/translator.ts`) as a non-fatal stage; translations are pure translations
  of validated content — never new research.
- Charts: `assets/<date>-<slug>/charts.json` series are rendered as theme-aware
  inline SVG on the report page (`src/charts.ts`); each chart carries a
  `source_id` pointing at an evidence object. Images placed under `assets/` can
  be referenced from report markdown as `assets/...`.

## Governance

See `AGENTS.md`: the daily job may only write `reports/ research/ memory/
public/` (enforced in `src/publisher.ts`); pipeline changes go through the
manual `maintenance.yml` workflow.
